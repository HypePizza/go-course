##### Как устроен план

За 12–14 недель консольный склад из текущего задания вырастет в HTTP-сервис с базой данных, тестами и Docker. Каждый этап доучивает одну тему и сразу применяет её к тому же проекту.

##### Этап 3. Конкурентность → v0.4 (недели 5–7)

Самая важная и сложная тема Go, поэтому на неё три недели. После неё склад безопасно работает из многих горутин — без этого HTTP-сервер на следующем этапе будет с гонками данных.

**Темы:** горутины; каналы (буферизованные, закрытие, `range` по каналу); `select` и таймауты; `sync.WaitGroup`, `sync.Mutex`, `sync.RWMutex`, `sync.Once`; `context.Context` (отмена, дедлайны); `errgroup`; детектор гонок `-race`; утечки горутин; паттерны worker pool, pipeline, fan-out/fan-in.

**Разминка:**

1. Запустите 1000 горутин, каждая делает `counter++`. Увидьте неверный результат, запустите с `-race`, исправьте тремя способами: `Mutex`, канал, `atomic.Int64`.
2. Worker pool: N воркеров считают SHA-256 для списка файлов, результаты собираются в одной горутине. Добавьте отмену через `context` по Ctrl+C (`signal.NotifyContext`).
3. Pipeline из трёх стадий (генератор → фильтр → сумматор). Убедитесь, что при отмене все горутины завершаются.
4. Функция, которая выполняет задачу с таймаутом через `select` и `context.WithTimeout`.

**Задание по проекту:**

- Сделайте `MemoryRepo` и `FileRepo` потокобезопасными. Объясните, где нужен `RWMutex`, а где достаточно `Mutex`.
- Важная деталь: проверка «хватает ли товара» и списание должны быть одной атомарной операцией. Напишите тест: 100 горутин одновременно снимают по 1 единице с остатка 50 — успешных снятий ровно 50, остаток 0.
- Команда `import` обрабатывает несколько CSV-файлов параллельно (worker pool или `errgroup` с `SetLimit`), в конце печатает сводку.
- Фоновая горутина «низкий остаток»: раз в N секунд (`time.Ticker`) пишет предупреждение для товаров ниже порога и корректно останавливается по `context`.
- Методы сервиса и репозитория принимают `ctx context.Context` первым аргументом — подготовка к HTTP и базе.

**Готово, когда:** `go test -race ./...` зелёный; после Ctrl+C программа завершается за секунду и не оставляет полузаписанный файл; вы можете нарисовать, какие горутины живут в программе и кто их останавливает.

##### Этап 4. HTTP API → v0.5 (недели 8–9)

Склад становится REST-сервисом на стандартной библиотеке. Фреймворки (Gin, Echo, chi) — только после того, как всё работает на `net/http`: так понятно, что они делают за вас.

**Темы:** `net/http`, `http.Handler` и `HandlerFunc`; маршруты `ServeMux` с методами и параметрами (`GET /items/{sku}`, `r.PathValue`); JSON в запросах и ответах; коды статуса; middleware (логирование, recover, request ID); структурные логи `log/slog`; таймауты `http.Server`; graceful shutdown; `httptest`; HTTP-клиент с таймаутом.

**Разминка:**

1. Сервер «гостевая книга»: `GET /messages` и `POST /messages`, данные в памяти под мьютексом.
2. Middleware, который логирует метод, путь, статус и длительность. Для статуса придётся обернуть `ResponseWriter` — хорошее упражнение на встраивание.
3. Консольный клиент, который параллельно запрашивает 5 URL и печатает статус и время ответа (пригодится этап 3).

**Задание по проекту:**

- Эндпоинты: `GET /items`, `GET /items/{sku}`, `POST /items`, `POST /items/{sku}/remove`, `GET /items/{sku}/history`, `GET /health`.
- Ошибки домена превращаются в HTTP-коды в одном месте: `ErrNotFound` → 404, `*ShortageError` → 409 с полями `have`/`need` в JSON, валидация → 400, остальное → 500 без деталей наружу.
- Пагинация и фильтр для списка: `?limit=20&offset=40&q=болт`.
- Конфигурация через переменные окружения (порт, путь к файлу, уровень логов).
- Graceful shutdown: по SIGTERM сервер доделывает текущие запросы, останавливает фоновую горутину и сохраняет данные.
- Структура папок по слоям: `cmd/warehouse` (CLI), `cmd/server`, `internal/inventory` (домен), `internal/storage`, `internal/httpapi`.

**Готово, когда:** все обработчики покрыты табличными тестами через `httptest`; сценарий из этапа 3 (100 параллельных снятий) проходит уже через HTTP под `-race`; `curl` на несуществующий SKU возвращает 404 с понятным JSON.

##### Этап 5. База данных → v0.6 (недели 10–11)

Третья реализация `Repository` — на PostgreSQL. Здесь окупается интерфейс из этапа 1: сервис и HTTP-слой не меняются.

**Темы:** `database/sql` (пул соединений, `QueryContext`, `Scan`, `sql.ErrNoRows`, закрытие `rows`); драйвер `pgx`; транзакции и блокировки (`SELECT … FOR UPDATE`); параметризованные запросы и SQL-инъекции; миграции (`goose` или `golang-migrate`); генерация кода из SQL через `sqlc` (по желанию); интеграционные тесты с настоящей базой в Docker.

**Разминка:**

1. Поднимите PostgreSQL в Docker, создайте таблицу заметок и напишите CRUD на `database/sql` без сторонних библиотек, кроме драйвера.
2. Перевод денег между двумя счетами в транзакции. Намеренно уроните вторую запись и убедитесь, что первая откатилась.

**Задание по проекту:**

- Таблицы `items` и `movements` (история операций) через миграции. Ограничение `CHECK (qty >= 0)` — вторая линия защиты.
- `PostgresRepo`: снятие товара и запись в `movements` — в одной транзакции. Сравните два подхода: `FOR UPDATE` и атомарный `UPDATE … SET qty = qty - $1 WHERE qty >= $1`.
- Выбор хранилища переменной окружения: `memory`, `file` или `postgres`.
- Один набор контрактных тестов для всех трёх реализаций `Repository`. Тесты с Postgres запускаются отдельно (build tag или `testing.Short()`).

**Готово, когда:** тест на 100 параллельных снятий проходит и на Postgres; в коде нет SQL, собранного через `fmt.Sprintf`; ни один `rows` не остаётся незакрытым.

##### Этап 6. Продакшен-навыки → v1.0 (недели 12–14)

Итог всего плана — проект, который не стыдно показать на собеседовании: он собирается одной командой, проверяется в CI и запускается в Docker.

**Темы:** многоступенчатая сборка Docker и `docker compose`; `Makefile` или `Taskfile`; линтер `golangci-lint`; GitHub Actions; бенчмарки (`testing.B`) и профилирование `pprof`; фаззинг (`testing.F`); метрики Prometheus; аутентификация по токену; документация API (OpenAPI).

**Задание по проекту:**

- `Dockerfile` (сборка на `golang`, запуск на `distroless` или `scratch`) и `compose.yaml` с сервисом и Postgres. `docker compose up` — и всё работает.
- CI на GitHub Actions: `go vet`, `golangci-lint`, тесты с `-race`, интеграционные тесты с Postgres как service container.
- Бенчмарк `List()` на 10 000 товаров. Найдите узкое место через `pprof`, ускорьте и сравните через `benchstat`.
- Фазз-тест для парсинга `Money` из строки.
- Эндпоинт `/metrics`: число запросов, длительность, число ошибок нехватки.
- Изменяющие запросы требуют токен в заголовке `Authorization` (middleware).
- README: что это, как запустить, примеры `curl`, архитектура слоёв.

**Готово, когда:** человек с нуля клонирует репозиторий и запускает сервис за 5 минут по README; CI зелёный; у вас есть цифра «было/стало» из бенчмарка.

**Что дальше** (на выбор после v1.0): gRPC и protobuf; очереди (Kafka, NATS) для событий склада; кэш на Redis; разбиение на два сервиса (склад и заказы).

##### Как пользоваться планом

План рассчитан на 7 модулей примерно по 1–2 недели каждый при 6–8 часах в неделю. Предполагается, что базовый синтаксис (переменные, `if`, `for`, функции) вы уже знаете.

Каждый модуль устроен одинаково:

1. **Теория** — что прочитать и понять. Читайте до начала задач, но не дольше 1–2 вечеров.
2. **Практика по языку** — короткие упражнения, проверяющие именно механику Go.
3. **Алгоритмические задачи** — от простой к сложной. Сначала решение на бумаге: идея, сложность по времени и памяти, крайние случаи. Только потом код.
4. **Мини-проект** — небольшая программа, где теория и алгоритмы складываются вместе.
5. **Контрольные вопросы** — если не можете ответить без подсказки, вернитесь к теории.

Правила, которые развивают алгоритмическое мышление:

- Перед кодом пишите в комментарии: входные данные, выходные данные, идея, O(…) по времени и памяти.
- К каждой задаче пишите табличный тест (`go test`) с крайними случаями: пустой ввод, один элемент, дубликаты, отрицательные числа.
- Застряли больше чем на 40 минут — посмотрите подсказку или разбор, затем через 2–3 дня решите задачу заново с нуля.
- Решённую задачу попробуйте улучшить: меньше памяти, меньше проходов, другой подход.

Окружение: актуальная версия Go с [go.dev/dl](https://go.dev/dl/), редактор с `gopls` (VS Code или GoLand), один репозиторий `go-learning` с папкой на каждый модуль. Привычка с первого дня: `go vet`, `gofmt`, `go test -race`.

##### Модуль 1. Указатели (1–2 недели)

Цель: понимать, что копируется при каждом присваивании и вызове функции, и сознательно выбирать между значением и указателем.

###### Теория

- Операторы `&` (взять адрес) и `*` (разыменование), тип `*T`, нулевое значение `nil`.
- В Go всё передаётся по значению. Указатель — тоже значение, копируется адрес.
- `new(T)` против `&T{}`; почему в Go можно вернуть адрес локальной переменной (escape analysis: `go build -gcflags=-m`).
- Стек и куча на уровне интуиции; сборщик мусора и отсутствие арифметики указателей.
- Указатели на структуры: авторазыменование `p.Field` вместо `(*p).Field`.
- Указатель на указатель `**T` и когда он нужен (изменить сам указатель внутри функции).
- Когда указатель не нужен: маленькие структуры, слайсы и мапы уже содержат ссылку на данные.
- Паника `nil pointer dereference`: как читать стектрейс.

###### Практика по языку

- [ ] `swap(a, b *int)` — обмен значений. Затем объясните, почему `swap(a, b int)` не работает.
- [ ] Напишите `incrementValue(x int)` и `incrementPtr(x *int)`, выведите адреса через `fmt.Printf("%p")` до и после вызова.
- [ ] Структура `Counter{n int}` и функция `reset(c Counter)`. Почему счётчик не сбрасывается? Исправьте.
- [ ] Функция `setToNil(p **int)` — обнулить указатель вызывающей стороны.
- [ ] Спровоцируйте панику на `nil`-указателе, затем добавьте защитную проверку.
- [ ] Запустите `go build -gcflags=-m` на функции `func newInt() *int { x := 42; return &x }` и найдите строку `moved to heap`.

###### Алгоритмические задачи

#### Урок 1. Модуль, пакеты, импорты и `main`

##### Зачем это нужно
Любая программа на Go, от маленькой утилиты до микросервиса, устроена одинаково: это модуль, внутри него пакеты, а запуск начинается с функции `main`. В рабочем проекте на сотни файлов вы будете постоянно разбираться, какой пакет что импортирует и что из него видно снаружи.

##### Объяснение

**Модуль** — это ваш проект. Его описывает файл `go.mod`, в котором записаны имя модуля и версия Go. Ближайшие аналоги: `requirements.txt` в Python или Makefile в C, но `go.mod` встроен в сам язык.

```bash
mkdir hello && cd hello
go mod init hello
```

Появится `go.mod` с двумя строками: `module hello` и строка `go` с вашей версией. В реальных проектах модуль называют по адресу репозитория, например `github.com/yourname/hello`. Пока хватит простого `hello`.

**Пакет** — это папка с `.go`-файлами. Все файлы в одной папке принадлежат одному пакету. Особый пакет `main` с функцией `main()` — точка входа исполняемой программы.

Структура проекта:
```
hello/
├── go.mod
├── main.go
└── greet/
    └── greet.go
```

**Файл `greet/greet.go`:**
```go
package greet

import "fmt"

// Hello начинается с заглавной буквы, поэтому видна из других пакетов
func Hello(name string) string {
	return fmt.Sprintf("Привет, %s!", decorate(name))
}

// decorate начинается со строчной буквы, это приватная функция пакета
func decorate(name string) string {
	return "*" + name + "*"
}
```

**Файл `main.go`:**
```go
package main

import (
	"fmt"
	"os"

	"hello/greet" // импорт своего пакета: имя модуля + путь к папке
)

func main() {
	// os.Args[0] — путь к программе, дальше идут аргументы командной строки
	name := "мир"
	if len(os.Args) > 1 {
		name = os.Args[1]
	}
	fmt.Println(greet.Hello(name))
}
```
`:=` и `if` подробно разберём в следующих уроках. Пока достаточно знать, что `:=` объявляет переменную.

**Запуск:**
```bash
go run .            # скомпилировать во временную папку и сразу запустить
go run . Анна       # то же самое, но с аргументом
go build            # собрать бинарник hello в текущей папке
./hello Анна        # → Привет, *Анна*!
```

##### Сравнение с C и Python
- **Сборка.** В C вы вызываете `gcc`, следите за `.h`-файлами и линковкой. В Go `go build` сам находит все пакеты и собирает **один статический бинарник**. Его можно скопировать на другую машину без установленного Go. Python-скрипт так не запустить без интерпретатора.
- **Видимость.** В Python `_name` — только договорённость, такую функцию всё равно можно вызвать. В C для сокрытия пишут `static`. В Go правило задаёт регистр первой буквы, и компилятор его **принуждает**: `Hello` экспортирована, `decorate` нет.
- **Заголовочных файлов нет.** Пакет импортируют целиком, а обращаются к его функциям через имя пакета: `greet.Hello`.

##### Типичные ошибки
1. **Неиспользуемый импорт или переменная — это ошибка компиляции**, а не предупреждение, как в C. Python о таком вообще молчит. Поначалу это раздражает, зато код остаётся чистым.
2. **Открывающая фигурная скобка на новой строке.** Это привычка из некоторых стилей C, и в Go это синтаксическая ошибка: компилятор сам расставляет `;` в конце строк. Скобка всегда остаётся на той же строке, что и `func` или `if`.
3. **`go run main.go`, когда в пакете несколько файлов.** Тогда компилятор не увидит остальные файлы и выдаст `undefined`. Привыкайте писать `go run .`.
4. **Запуск без `go mod init`.** Получите ошибку вида `cannot find main module`.
5. **Форматирование вручную.** Отступы в Go делаются табами, а форматирует код `gofmt`. Настройте форматирование при сохранении в редакторе (VS Code + расширение Go или GoLand) и не спорьте с ним.

##### Про `byte` и `rune`

Про `byte` вы правы наполовину. Он действительно псевдоним `uint8`, поэтому `%T` печатает `uint8`: это **один и тот же тип** под двумя именами, а не два разных. Но называть `byte` символом неверно. Это просто **байт**, число от 0 до 255. В C `char` тоже, по сути, однобайтовое число. Символом его считали, пока тексты были на латинице в ASCII.

Строки в Go хранятся в **UTF-8**. Латинская буква занимает 1 байт, русская 2 байта, эмодзи 4 байта. Один байт больше не равен одному символу, поэтому нужен отдельный тип.

**`rune` — это номер символа в Unicode** (code point). Номера доходят до 1 114 111, в 16 бит они не помещаются, поэтому `rune` — псевдоним `int32`.

```go
s := "Привет"
fmt.Println(len(s))                    // 12 — len считает байты!
fmt.Println(utf8.RuneCountInString(s)) // 6 — а символов 6 (пакет unicode/utf8)

r := 'П'                          // одинарные кавычки — это руна, а не строка
fmt.Printf("%c %d %T\n", r, r, r) // П 1055 int32
```

**Подвох для тех, кто пришёл из Python:** в Python `s[0]` — первый *символ*. В Go `s[0]` — первый *байт*. Для `"Привет"` это будет 208, то есть половина буквы «П». Подробно разберём строки, байты и руны в модуле 2. Пока запомните главное: **`byte` — единица хранения, `rune` — символ**.

Вы правильно поняли причину: `break` внутри `switch` выходит из `switch`, а не из цикла. Именно поэтому строка «отрицательное, стоп» печаталась 7 раз. Задание засчитано. Предсказанный вывод вы не прислали, но объяснение показывает, что поведение вы поняли.

**Вариант 2 (`if` вместо `switch`) лучший.** У `switch` с двумя ветками нет преимуществ перед `if`, а у `if` нет такой ловушки. Самое простое исправление часто бывает и самым правильным.

**Вариант 1 работает, но `goto` здесь не нужен.** В Go `goto` есть, но в обычном коде его почти не используют. Для выхода из цикла изнутри `switch` есть **`break` с меткой**, и это как раз то, что разбиралось в уроке:

```go
loop:
	for i := range 10 {
		v := 5 - i*2
		switch {
		case v < 0:
			fmt.Println("отрицательное, стоп")
			break loop // выход из цикла, а не из switch
		default:
			fmt.Println(v)
		}
	}
```

Чем этот вариант лучше `goto`:
- Метка стоит **перед циклом**, из которого выходим, поэтому сразу понятно, что именно прерывается. У вас метка `Outerloop` стоит перед *вторым* циклом, и её название вводит в заблуждение.
- `goto` может прыгнуть куда угодно в пределах функции, а `break loop` делает только одно: выходит из этого цикла.

Есть и третий способ, который часто встречается в реальном коде: вынести цикл в функцию и выходить через `return`.

##### Как проверять все случаи разом

###### Вариант 1: однострочник для простых случаев

```bash
for a in 12 97 1 0 abc; do echo "== $a"; go run . $a; echo "exit=$?"; done
```

Разберём по частям:
- `for a in 12 97 1 0 abc; do ... done` — цикл: переменная `a` по очереди принимает каждое значение.
- `echo "== $a"` — заголовок, чтобы было видно, какой случай сейчас выполняется.
- `$?` — код выхода **последней** выполненной команды: 0 означает успех, 1 — ошибку.

**Подвох в zsh**, а на macOS по умолчанию стоит именно он. Если в одном случае два аргумента, например `"1.5 GB"`, zsh передаст их программе **одной строкой** `"1.5 GB"`, а не двумя аргументами. Bash в такой ситуации разбивает строку на две части, а zsh нет. Чтобы zsh тоже разбил строку, пишите `${=a}` вместо `$a`. Удобнее, впрочем, второй вариант.

###### Вариант 2: скрипт `check.sh` рядом с решением (рекомендую)

Набирать цикл заново каждый раз неудобно. Сохраните его в файл и закоммитьте вместе с решением:

```bash
#!/usr/bin/env bash
# Прогон всех случаев из условия задачи
go build -o bin/hsize . || exit 1   # собираем один раз, дальше запуск мгновенный

cases=(
  "512"
  "1536"
  "1.5 GB"
  "2.7 B"
  "abc"
  "10 xb"
  ""          # без аргументов
  "1 2 3"     # лишние аргументы
)

for c in "${cases[@]}"; do
  echo "\$ hsize $c"
  ./bin/hsize $c 2>&1 | cat -e
  echo "exit=${PIPESTATUS[0]}"
done
```

Запуск из папки задачи:
```bash

```

Что здесь происходит:
- **`#!/usr/bin/env bash`** — скрипт выполняется в bash, поэтому подвох с zsh не мешает: `"1.5 GB"` правильно передаётся как два аргумента, а `""` — как запуск без аргументов.
- **`go build -o bin/hsize .`** — программа собирается один раз, это быстрее, чем `go run` для каждого случая. Папка `bin/` уже есть в `.gitignore`. Часть `|| exit 1` означает: если сборка упала, скрипт сразу останавливается.
- **`2>&1`** — stderr перенаправляется туда же, куда stdout, поэтому сообщения об ошибках тоже проходят через `cat -e`.
- **`| cat -e`** — показывает `$` в конце каждой строки, поэтому сразу видны лишние пробелы и забытый `\n`.
- **`${PIPESTATUS[0]}`** — код выхода **вашей программы**. Здесь важная тонкость: если написать `$?` после конвейера `prog | cat -e`, получится код выхода **`cat`**, а он почти всегда равен 0. Я сам на это наткнулся, когда проверял ваш код.

Программа работает правильно, «ломает» буквы только `cat -e` на macOS.

**Почему так происходит.** В UTF-8 каждая русская буква занимает **2 байта**, и оба байта больше 127. Версия `cat` на macOS вместе с `-e` включает режим `-v`, который показывает такие байты в виде `M-...`. Часть байтов она заменяет, часть оставляет как есть, и терминал уже не может собрать из них буквы. Латиница, цифры и `$` проходят без изменений, поэтому `"xb"`, `B, KB, MB` читаются нормально. Это то самое «один символ ≠ один байт», о котором мы говорили про `byte` и `rune`.

На Linux `cat -e` из GNU coreutils ведёт себя похоже, но на моей машине кириллица тоже превращалась в `M-...`. Так что дело не в вашем Mac, а в самом флаге.

**Решение.** Вместо `cat -e` используйте `perl` (на macOS он установлен по умолчанию). Эта команда только дописывает `$` перед каждым переводом строки и больше ничего не трогает:

```bash
./bin/hsize $c 2>&1 | perl -pe 's/\n/\$\n/'
```

Результат:
```
ошибка: неизвестная единица "xb", нужна B, KB, MB, GB, TB или PB$
```

Если `\n` в конце забыт, `$` не появится, и следующая строка приклеится к выводу. То есть ошибка по-прежнему будет видна:
```
ошибка: тест  $        ← два пробела в конце видны перед $
без перевода           ← нет $ → забыт \n
exit=1
```

В `check.sh` замените строку на:
```bash
  ./bin/hsize $c 2>&1 | perl -pe 's/\n/\$\n/'
  echo "exit=${PIPESTATUS[0]}"
```

`${PIPESTATUS[0]}` по-прежнему показывает код выхода вашей программы, а не `perl`.

Для сравнения с эталоном через `diff` всё это не нужно: `diff` сравнивает байты напрямую и с кириллицей работает без проблем.

Файл удаляется так же, как изменяется: удаляешь, коммитишь, пушишь. Есть два варианта.

###### 1. Удалить совсем, и с диска, и из репозитория

```bash
git rm путь/к/файлу
git commit -m "Удалить файл"
git push
```

`git rm` удаляет файл и сразу добавляет это удаление в коммит. Можно удалить файл и обычным способом (`rm` или в Finder), но тогда перед коммитом понадобится `git add путь/к/файлу`: удаление тоже нужно добавить.

Для папки: `git rm -r путь/к/папке`.

###### 2. Убрать из репозитория, но оставить на диске

Это типичный случай, когда в репозиторий случайно попал бинарник после `go build`:

```bash
git rm --cached путь/к/файлу
echo "путь/к/файлу" >> .gitignore
git add .gitignore
git commit -m "Убрать бинарник из репозитория"
git push
```

Флаг `--cached` убирает файл только из git, а файл на диске остаётся. Запись в `.gitignore` нужна, чтобы при следующем `git add .` он не попал в репозиторий снова.

###### Важный момент

Удаление создаёт **новый коммит**. В старых коммитах файл остаётся, и на GitHub его можно найти через историю. Для бинарника это неважно. У `diff` всегда два аргумента: что сравнивать и с чем. Когда второй вход приходит через `|`, на его месте ставят **`-`**, это значит «читать из стандартного ввода»:

```bash
bash ./check.sh | diff expected.txt -
```

Если файлы совпадают, `diff` ничего не выводит и возвращает код 0. Проверить код можно так:

```bash
bash ./check.sh | diff expected.txt - && echo OK
```

Если вывод отличается, удобнее читать в формате `-u`, как у `git diff`:

```bash

```

Здесь `-` в начале строки значит «ожидалось, но не пришло», а `+` значит «пришло, но не ожидалось».


`<(...)` подставляет вывод команды как временный файл.

Одна ловушка: если программа пишет ошибки в stderr, через `|` они не пройдут, и `diff` их не увидит. Поэтому в `check.sh` у каждого запуска должно стоять `2>&1`.
