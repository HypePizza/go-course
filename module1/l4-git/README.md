# Мини-тема. Git и GitHub

> Модуль 1 «Старт» · macOS

## Зачем это нужно

Git есть в любой команде разработчиков: через него хранят историю кода, откатывают неудачные правки и проводят код-ревью. А публичный GitHub с вашими проектами — первое, что откроет работодатель после резюме. Начнём складывать туда курс уже сейчас, чтобы к собеседованиям там была история за полгода.

## Объяснение

### Основная идея

Git хранит **снимки** (коммиты) вашего проекта. Каждый коммит — это состояние всех файлов в какой-то момент плюс сообщение «что и зачем изменилось». К любому коммиту можно вернуться.

Файл проходит три состояния:

```
рабочая папка  ──git add──▶  staging (индекс)  ──git commit──▶  история
(вы правите)                 (что войдёт в коммит)              (снимок сохранён)
```

Staging нужен, чтобы в один коммит попали только связанные изменения, а не всё подряд.

### Настройка (один раз)

```bash
git --version   # на macOS при первом запуске предложит установить Command Line Tools

git config --global user.name "Dmitriy ..."
git config --global user.email "почта@от.github"
git config --global init.defaultBranch main
```

### Ежедневный цикл

```bash
cd go-course
git init                     # создать репозиторий (один раз)

git status                   # что изменилось — запускайте постоянно
git diff                     # сами изменения построчно
git add 03-if-for-switch/    # добавить в staging папку или файл
git commit -m "Урок 3: решение задачи о простых числах"
git log --oneline            # история коммитов
```

### `.gitignore`

Файл со списком того, что Git не должен отслеживать. Бинарники в репозиторий **не кладут** — их всегда можно собрать заново из кода.

```gitignore
# Бинарники
bin/
*.exe

# Системные файлы macOS
.DS_Store
```

Чтобы бинарники всегда попадали в `bin/`, собирайте так:

```bash
go build -o bin/ .
```

### Ветки

Ветка — отдельная линия изменений. Основная ветка — `main`; новую работу делают в отдельной ветке, а потом сливают.

```bash
git switch -c fix-naming     # создать ветку и перейти в неё
# ... правки, add, commit ...
git switch main              # вернуться в main
git merge fix-naming         # влить изменения
git branch -d fix-naming     # удалить ветку, она больше не нужна
```

В командах вместо `merge` в `main` создают **Pull Request** на GitHub — по нему коллеги делают код-ревью. Этим мы займёмся в проекте.

### GitHub

1. Зарегистрируйтесь на [github.com](https://github.com).
2. Создайте SSH-ключ и добавьте его в GitHub — так не придётся вводить пароль:
   ```bash
   ssh-keygen -t ed25519 -C "почта@от.github"   # Enter на все вопросы
   pbcopy < ~/.ssh/id_ed25519.pub               # скопировать публичный ключ
   ```
   Вставьте его на GitHub: **Settings → SSH and GPG keys → New SSH key**. Проверка: `ssh -T git@github.com`.
3. Создайте на GitHub пустой репозиторий `go-course` (без README и `.gitignore` — они у вас уже есть).
4. Свяжите и отправьте:
   ```bash
   git remote add origin git@github.com:ВАШ_ЛОГИН/go-course.git
   git push -u origin main      # -u нужен только первый раз
   ```
   Дальше достаточно `git push`.

### Хорошее сообщение коммита

- Коротко, по делу, **что** изменилось: `Урок 2: задачи на iota и приведение типов`.
- Один коммит — одно логическое изменение.
- Плохо: `fix`, `asdf`, `изменения`, `final2`.

## Сравнение с C и Python

Тут сравнивать не с чем: Git не зависит от языка. Но есть связь с Go: **путь модуля в `go.mod` обычно совпадает с адресом репозитория** — `module github.com/ваш-логин/project`. Именно по этому адресу другие смогут сделать `go get` вашего пакета.

## Типичные ошибки

1. **`git add .` не глядя.** В коммит попадают бинарники, `.DS_Store` и случайные файлы. Сначала `git status`, потом `add`.
2. **Секреты в репозитории.** Пароли, токены и ключи не коммитят никогда — даже если потом удалить файл, они останутся в истории. Для них есть переменные окружения (модуль 7).
3. **Огромные коммиты «за неделю».** Коммитьте после каждого законченного шага.
4. **Отправка приватного SSH-ключа.** На GitHub загружается только файл с `.pub` на конце.
