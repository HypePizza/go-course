## Зачем нужны defer, panic и recover

Представь, что ты открыл файл с показаниями датчика. Дальше у функции три пути: вернуть результат, выйти раньше из-за ошибки в данных или прерваться из-за неожиданного сбоя. Закрытие файла удобно запланировать сразу после успешного открытия. В Go для этого есть `defer`.

`panic` прерывает обычное выполнение. Пока паника поднимается по цепочке вызовов, Go выполняет отложенные действия каждой покидаемой функции. `recover` позволяет остановить панику там, где вызывающий код готов обработать такой сбой. Для ожидаемых проблем вроде неверного числа в аргументах по-прежнему подходит знакомый тебе `error`.

## Когда вычисляется значение

```go
package main

import "fmt"

func inspect() {
	stage := "старт"
	defer fmt.Println("аргумент:", stage)
	defer func() {
		fmt.Println("замыкание:", stage)
	}()

	stage = "готово"
	fmt.Println("тело")
}

func main() {
	inspect()
	fmt.Println("после inspect")
}
```

Вывод:

```text
тело
замыкание: готово
аргумент: старт
после inspect
```

Когда выполнение доходит до первого `defer`, Go вычисляет аргументы будущего вызова. В этот момент `stage` содержит строку «старт». Второй `defer` регистрирует вызов замыкания. Как в твоём `newTotal`, у замыкания есть доступ к переменной. Оно прочитает `stage`, когда начнёт выполняться. При выходе из `inspect` последним зарегистрированное действие выполняется первым.

У `return` тоже есть порядок. Сначала выражения после `return` задают значения результатов функции, затем выполняются отложенные вызовы, затем результаты получает вызывающий код. Если результат именован, отложенное замыкание может успеть его изменить.

## Что происходит при панике

Прочитай фрагмент как цепочку вызовов. Представь, что `main` вызывает `inspectJob()`, а следующей строкой печатает «дальше».

```go
func brokenJob() {
	defer fmt.Println("уборка")
	panic("сбой")
}

func inspectJob() {
	defer func() {
		if reason := recover(); reason != nil {
			fmt.Println("перехвачено:", reason)
		}
	}()
	brokenJob()
	fmt.Println("работа завершена")
}
```

Сначала появится «уборка» из `brokenJob`, затем «перехвачено: сбой» из отложенной функции в `inspectJob`. После восстановления `inspectJob` завершится и управление вернётся в `main`, который напечатает «дальше». Строка «работа завершена» пропускается. Так можно изолировать вызов отдельного обработчика и передать решение о следующей операции вызывающему коду.

## Сравнение с C и Python

| Ситуация | Go | Знакомая аналогия |
|---|---|---|
| Несколько ранних выходов | После получения ресурса можно поставить `defer closeResource()` | В C освобождение часто собирают в одном блоке очистки. В Python для файла обычно используют `with`, для произвольной очистки — `finally`. |
| Некорректный ввод | Функция возвращает `error`, вызывающий код проверяет его | В C часто проверяют код возврата. В Python преобразование некорректной строки в число вызывает `ValueError`. |
| Вызванный обработчик аварийно прервался | Его отложенные действия выполняются, а вызывающая функция может перехватить панику через свой `defer` | В Python после `except` можно продолжить ту же функцию. В Go функция, остановившая панику в своём отложенном вызове, завершает работу и возвращает управление выше. |

## Типичные ошибки

- **Поставить очистку до проверки ошибки.** Сначала убедись, что ресурс получен, затем регистрируй его освобождение.
- **Ожидать очистку в конце итерации.** Вызовы, зарегистрированные через `defer` внутри цикла, ждут выхода из окружающей функции. Если каждый ресурс нужен только на одну итерацию, обработку одного элемента можно вынести в функцию.
- **Вызвать `recover` через лишнюю обёртку.** Для перехвата паники `recover()` должна вызвать непосредственно отложенная функция в той же горутине. При обычном завершении `recover()` вернёт `nil`.
- **Завершить процесс слишком рано.** `os.Exit` пропускает отложенные вызовы. В CLI удобно сначала вернуть ошибку из рабочей функции, дать её очистке выполниться и только потом выбрать код выхода в `main`.

```go
func trace(stop bool) {
	n := 2
	defer fmt.Println("A", n)
	n++
	defer func() { fmt.Println("B", n) }()
	if stop {
		return
	}
	n *= 2
	defer fmt.Println("C", n)
}
```

До запуска выпиши для каждого вызова две вещи: какие действия успели зарегистрироваться и какие строки появятся на экране. После запуска сравни с прогнозом. Затем замени только первый отложенный вызов на замыкание, которое читает `n`. Предскажи, какие строки изменятся, и проверь. На ревью пришли исходный прогноз и объясни хотя бы одну строку через момент чтения `n`.

## Задание 2. Одна очистка на три пути

**40–60 минут.** Папка — `task2/` внутри папки урока. Напиши функцию со следующей сигнатурой:

```go
func readSample(raw string, begin func() error, finish func()) (int, error)
```

Это модель сеанса чтения. `begin` открывает сеанс. Если он вернул ошибку, передай её вызывающему коду. После успешного открытия преобразуй `raw` в целое через `strconv.Atoi`. При неверном вводе верни ошибку, при успехе — число. Для обоих путей после открытия `finish` должен отработать ровно один раз. При ошибке числовой результат равен нулю.

В `main` передай функции, которые записывают события «открытие» и «закрытие» или просто печатают их. После каждого вызова выведи результат. Все случаи можно проверить одним запуском.

| Вход | Результат открытия | Число | Ошибка | Сколько закрытий до печати результата |
|---|---|---:|---|---:|
| «17» | успех | 17 | нет | 1 |
| «abc» | успех | 0 | да | 1 |
| «17» | ошибка | 0 | да | 0 |

**Вопрос для ревью.** Почему расположение `defer` относительно проверки результата `begin()` меняет поведение третьего случая?

## Задание 3. Сбой одного обработчика

**60–100 минут.** Папка — `task3/`. Представь, что программа по очереди запускает независимые обработчики измерений. Один из них может запаниковать. Напиши функцию, которая запускает один обработчик и возвращает его результат в `main`:

```go
func runStep(name string, work func() error) (err error)
```

Если обработчик отработал успешно, верни `nil`. Если вернул обычную ошибку, передай её вызывающему коду. Если запаниковал, верни ошибку вида `<имя>: паника: <причина>`. Само решение о продолжении серии принадлежит `main`. Переменных уровня пакета для этого не требуется.

Проверь за один запуск четыре последовательных вызова. Имена и действия обработчиков заданы в таблице:

| Имя | Что сделает обработчик | Что должен получить вызывающий код |
|---|---|---|
| A | Вернёт `nil` | Успех |
| B | Вернёт ошибку «нет данных» | Ошибка «нет данных» |
| C | Зарегистрирует отложенную печать «очистка C», затем вызовет `panic("сбой")` | Сначала печать очистки, затем ошибка «C: паника: сбой» |
| D | Вернёт `nil` | Успех после сбоя C |

Пусть `main` печатает для успеха имя и «OK», для ошибки — текст ошибки. Тогда файл `expected.txt` для всей серии будет таким:

```text
A OK
нет данных
очистка C
C: паника: сбой
D OK
```

Из папки задания проверь `go run . | diff -u expected.txt -`. Для ревью объясни, почему строка `D OK` достижима и в какой момент именованный результат `err` получает значение при панике.
